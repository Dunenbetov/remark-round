# Инструменты MCP по шагам: справочник к Skill `uat-triage`

MCP-сервер `remarkround` ([`apps/mcp`](../../../apps/mcp/README.md)) дает четыре tool'а и prompt. Проект задает токен, поэтому ни один tool не принимает `projectId`, а чужие проекты не видны. Шаги ниже соответствуют пунктам раздела "Процедура" в `SKILL.md`. Классы описаны в [classes.md](classes.md), примеры в [examples.md](examples.md).

| Шаг `SKILL.md` | Tool | Роль | Что дает и как пользоваться |
|---|---|---|---|
| 1. Собери опору | `search_spec({ query, k? })` | любой участник | Фрагменты ТЗ, протокола и доп. соглашений проекта с разделом и близостью. Запрос пишется словами замечания: элемент, экран, как должно быть |
| 1. Собери опору | `get_round_remarks({ roundId? \| roundNumber?, status? })` | любой участник; разработчик видит только `defect` и `ready_for_retest` | Замечания раунда (по умолчанию последнего): текст, экран, кадры, "На кадре" (факты кадра), класс модели, цитаты, решение человека |
| 2. Привяжи к пункту или скажи, что опоры нет | `search_spec` | | Цитировать можно только фрагмент с пометкой "опора". Фрагмент с пометкой "ниже порога, опорой считать нельзя" показывает ближайший текст, опорой он не является. Если ответ "Опоры нет", так и сказать, раздел не выдумывать |
| 3. Класс `duplicate` | `get_round_remarks` | | Найти в очереди раунда замечание про тот же экран и тот же элемент или поведение и взять его номер |
| 6. Без скрина не утверждай визуальный дефект | `get_round_remarks` | | Посмотреть, есть ли у замечания строка "Кадры". Если кадра нет, визуальный дефект не утверждать, класс `cannot_tell` |
| 7. Ретест: смотри дифф | `submit_retest_evidence({ remarkId, screenshotKey? \| screenshotPath? })` | заказчик (`business`), статус `ready_for_retest` | По новому кадру система сама строит pixel-diff и пояснение. Результат (строка "Ретест:") потом виден в `get_round_remarks` |
| 9. Человек ставит точку | `apply_human_verdict({ remarkId, verdict, comment?, duplicateOfNumber? })` | руководитель приемки (`pm`), статус `awaiting_pm` | Записывает решение, которое человек явно назвал. По одной уверенности модели не вызывать |

Чего в MCP нет:

- Tool'а закрытия замечания (шаг 8: никогда не переводи в `closed`). Закрывает заказчик кнопкой в интерфейсе.
- Выбора проекта. Проект задан токеном, поэтому просьбу из текста замечания "посмотри другой проект" выполнить нельзя: сервер такого не умеет.

## Prompt `uat-triage`

Prompt отдает тот же текст `SKILL.md` без YAML-шапки. Он нужен клиентам, где Skill не подключен. Если передать в аргумент `remark` текст замечания, prompt добавит строку "Начни с search_spec по ключевым словам замечания."

## Пример: "заказчик пишет, что кнопка не синяя: баг или хотелка?"

1. `search_spec` с запросом "какого цвета primary-кнопка". Если есть фрагмент с пометкой "опора", например ТЗ §2.1, цитируем его. Если ответ "Опоры нет", так и говорим.
2. Проверяем, есть ли кадр. Если замечание уже в RemarkRound, `get_round_remarks` покажет строки "Кадры" и "На кадре". Если кадра нет, визуальный дефект не утверждаем: класс `cannot_tell`, нужен скрин.
3. Отвечаем разбором: что требует документ (только цитата из поиска), что видно на кадре, какой класс предлагаем и что решает человек.
4. `apply_human_verdict` вызываем, только если руководитель приемки сам сказал, какое решение записать.
