# ADR 016 — Уведомления внутри продукта: колокольчик о замечаниях и личная комната сокета

Дата: 2026-09-23  
Статус: принято. Меняет ADR 013, пункт «Дайджест „вас ждёт кнопка“ не заменяем»: журнал («ждут меня») остаётся очередью работы, колокольчик указывает на неё.

## Контекст

Команда владельца работает на бою с 21.09, активность низкая. Продукт асинхронный: узнать, что дошла твоя очередь, можно только открыв журнал. ADR 013 убрал почту вместе с таблицей `Notification`; колокольчик остался только для приглашений. Запрос владельца 23.09: руководителю приёмки и разработчику — «упало новое замечание», заказчику — «изменился статус», тихий звук для тех, кто в другой вкладке. Решения владельца: заказчику — вехи по всем замечаниям проекта, только вехи, без внутренних шагов модели; системные уведомления браузера — по желанию человека.

## Решение

- **Одна точка записи.** Уведомления создаёт `RemarksService.writeHistory` — там же и в той же транзакции, что строку истории (`NotificationsService.record`). Строка `Notification` — на адресата и строку истории: `userId`, `projectId`, `remarkId`, `changeId`, `role` (роль адресата на момент события), `readAt`. Данные события берутся из неизменяемой `RemarkStatusChange` по `changeId`, копий нет. `failRun` пишет историю напрямую и уведомлений не даёт: сбой прогона — не событие для человека.
- **Кому что — по действию, не по конечному статусу** (`apps/api/src/notifications/audience.ts`, чистая функция). `proposal` → руководителю «ждёт вас»; `verdict → defect` → разработчику «ждёт вас», заказчику «к сведению»; `verdict → change_request | duplicate` → заказчику «к сведению»; `verdict → unspecified | cannot_tell` → заказчику «ждёт вас»; `ready_for_retest` и `retest_result` → заказчику «ждёт вас»; `not_fixed` → разработчику «ждёт вас», заказчику «к сведению»; `close` → заказчику «к сведению». Остальное — никому: `retest` и `cancel` тоже заканчиваются в `ready_for_retest`, но «можно смотреть снова» говорит только «Готово» разработчика. Сторона руководителя — роли `pm` и legacy `admin`. Автор действия исключается всегда (так «другим заказчикам» получается само), отключённые — тоже. `kind` не хранится — выводится из правил и `role`.
- **Действовать = прочитать.** Действие человека по замечанию (строка истории с автором и `fromStatus`) гасит его непрочитанные по этому замечанию в той же транзакции.
- **Сбой уведомлений не стоит решения.** `record()` работает под `SAVEPOINT rr_notify`: любая ошибка откатывается до точки сохранения, пишется в лог, а вердикт, строка истории и статус коммитятся. Проверено настоящей ошибкой Postgres внутри точки (`notifications.spec`).
- **Только событие, без содержания (ADR 007).** `NotificationView` — вид события, откуда и куда, текущий статус, номер и раунд, кто (имя снимком и роль) и когда. Комментариев, пометок истории, предложения модели, черновика, цитат, советов и `runId` нет ни для одной роли. Суть замечания (`title`) — только если адресат сейчас может открыть карточку (`readable`): разработчику после ухода замечания от него — `null`.
- **Только свои строки в текущей роли.** `GET /auth/notifications` и счётчик непрочитанных фильтруют в SQL по `userId` и текущим membership (`OR [{ projectId, role }]`): убрали из проекта или сменили роль — прежние строки не видны. `POST /auth/notifications/read` меняет только строки самого человека (`userId`), в том числе скрытые сменой роли: «прочитать все» гасит и их. Маршруты личные, как `/auth/invitations`: токен MCP получает 404 в `JwtAuthGuard`.
- **Личная комната сокета `user:{id}`.** Сервер сам кладёт в неё каждый сокет при подключении, клиент туда не входит и ничего в неё не шлёт. Это не чат и не глобальный канал (docs/WS.md): в комнате только толчки своему человеку о его же строках. Сокет с токеном MCP (`scopedProjectId`) в неё не попадает — токен живёт внутри одного проекта. `revoke(user, project)` выводит сокеты из комнат замечаний проекта, а личную комнату оставляет и шлёт `notification.sync` — клиент перечитывает список, и фильтр в SQL убирает лишнее.
- **Толчок после коммита — через очередь.** `record()` ставит задачу `notify_push` в той же транзакции (`jobs.enqueue(…, { tx })`): воркер видит её только после коммита — транзакционный «ящик исходящих» без правки каждой транзакции. Обработчик собирает представления той же функцией, что список, и через `UserEvents` (шина в памяти, как `RunEvents`) отдаёт `notification.new` адресатам и `notification.read` автору. Повтор задачи после рестарта даёт дубль толчка — клиент сливает по `id`.
- **Правда — строка в БД, сокет — только толчок.** Восстановление пакетов socket.io живёт в памяти процесса и теряется при рестарте, поэтому клиент сверяется по REST при подключении и переподключении сокета, при открытии колокольчика и при возврате во вкладку.
- **Звук и системные уведомления — настройки устройства.** Звук только для «ждёт вас» и только когда ни одна вкладка RemarkRound не в фокусе; системное уведомление браузера — по переключателю, разрешение — только по клику, в тексте номер и раунд без сути. Сервер о них не знает.

## Последствия

- Колокольчик работает, пока открыта вкладка: писем и push-сервиса нет (ADR 013 в силе). Кто не открывает продукт, по-прежнему не узнает о своей очереди.
- Один инстанс API: `UserEvents` и комнаты socket.io — в памяти процесса. На втором инстансе толчок дойдёт только до сокетов того процесса, где выполнилась задача `notify_push`; список по REST останется верным. Для второго инстанса — тот же Redis-адаптер socket.io, что и для комнат замечаний (docs/ARCHITECTURE.md, «Один инстанс API»).
- Задача на каждое событие с адресатами: импорт журнала уведомлений не даёт (`import` — никому), разбор 200 строк — 200 предложений руководителю и столько же задач `notify_push`; разом их идёт не больше двух из восьми слотов воркера, прогонам графа и индексации места хватает.
- Миграция `20260924100000_notifications` только добавляет таблицу, индексы и четыре внешних ключа `ON DELETE CASCADE`; каскад от строки истории проходит триггер `rr_append_only`.
- Спеки: `notifications/audience.spec` (таблица правил, регресс `retest`/`cancel`), `notifications/notifications.spec` (рассылка, автор и отключённые, «действовать = прочитать», ADR 007, смена роли и удаление, страницы, прочтение, MCP — 404, изоляция SAVEPOINT), `gateway/ws.notifications.spec` (толчок, вторая вкладка, MCP-сокет, `notification.sync`), `remarks/labels.contract.spec` (у каждого правила есть фраза на экране).
