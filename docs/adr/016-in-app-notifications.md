# ADR 016: Уведомления внутри продукта (колокольчик о замечаниях и личная комната сокета)

Дата: 2026-09-23  
Статус: принято. Меняет пункт ADR 013 о дайджесте "вас ждет кнопка": журнал ("ждут меня") остается очередью работы, колокольчик указывает на нее.

## Контекст

Моя рабочая команда работает на проде с 21.09, активность низкая. Продукт асинхронный: узнать, что дошла твоя очередь, можно только открыв журнал. ADR 013 убрал почту вместе с таблицей `Notification`, колокольчик остался только для приглашений. Задача 23.09: руководителю приемки и разработчику сообщать "упало новое замечание", заказчику "изменился статус", а тем, кто в другой вкладке, подавать тихий звук. Решения: заказчику приходят вехи по всем замечаниям проекта, только вехи, без внутренних шагов модели; системные уведомления браузера включаются по желанию человека.

## Решение

- Точка записи одна. Уведомления создает `RemarksService.writeHistory` там же и в той же транзакции, что и строку истории (`NotificationsService.record`). Строка `Notification` заводится на адресата и строку истории: `userId`, `projectId`, `remarkId`, `changeId`, `role` (роль адресата на момент события), `readAt`. Данные события берутся из неизменяемой `RemarkStatusChange` по `changeId`, копий нет. `failRun` пишет историю напрямую и уведомлений не дает: сбой прогона для человека событием не считается.
- Адресаты выбираются по действию (`apps/api/src/notifications/audience.ts`, чистая функция): `proposal` → руководителю "ждет вас"; `verdict → defect` → разработчику "ждет вас", заказчику "к сведению"; `verdict → change_request | duplicate` → заказчику "к сведению"; `verdict → unspecified | cannot_tell` → заказчику "ждет вас"; `ready_for_retest` и `retest_result` → заказчику "ждет вас"; `not_fixed` → разработчику "ждет вас", заказчику "к сведению"; `close` → заказчику "к сведению". Остальные действия никому не приходят. `retest` и `cancel` тоже заканчиваются в `ready_for_retest`, но "можно смотреть снова" говорит только "Готово" разработчика, поэтому конечный статус адресатов не определяет. Сторона руководителя: роли `pm` и legacy `admin`. Автор действия исключается всегда (так "другим заказчикам" получается само), отключенные тоже. `kind` не хранится, он выводится из правил и `role`.
- Действовать значит прочитать. Действие человека по замечанию (строка истории с автором и `fromStatus`) гасит его непрочитанные по этому замечанию в той же транзакции.
- Сбой уведомлений не отменяет решение. `record()` работает под `SAVEPOINT rr_notify`: любая ошибка откатывается до точки сохранения и пишется в лог, а вердикт, строка истории и статус коммитятся. Проверено настоящей ошибкой Postgres внутри точки (`notifications.spec`).
- Уведомление несет только событие, без содержания (ADR 007). В `NotificationView` вид события, откуда и куда, текущий статус, номер и раунд, кто (имя снимком и роль) и когда. Комментариев, пометок истории, предложения модели, черновика, цитат, советов и `runId` нет ни для одной роли. Суть замечания (`title`) отдается, только если адресат сейчас может открыть карточку (`readable`): разработчику после ухода замечания от него приходит `null`.
- Человек видит только свои строки в текущей роли. `GET /auth/notifications` и счетчик непрочитанных фильтруют в SQL по `userId` и текущим membership (`OR [{ projectId, role }]`): если человека убрали из проекта или сменили ему роль, прежние строки не видны. `POST /auth/notifications/read` меняет только строки самого человека (`userId`), в том числе скрытые сменой роли: "прочитать все" гасит и их. Маршруты личные, как `/auth/invitations`: токен MCP получает 404 в `JwtAuthGuard`.
- У каждого человека есть личная комната сокета `user:{id}`. Сервер сам кладет в нее каждый сокет при подключении, клиент туда не входит и ничего в нее не шлет. Чатом или глобальным каналом она не служит (docs/WS.md): в комнате только толчки своему человеку о его же строках. Сокет с токеном MCP (`scopedProjectId`) в нее не попадает, потому что токен живет внутри одного проекта. `revoke(user, project)` выводит сокеты из комнат замечаний проекта, а личную комнату оставляет и шлет `notification.sync`: клиент перечитывает список, и фильтр в SQL убирает лишнее.
- Толчок после коммита идет через очередь. `record()` ставит задачу `notify_push` в той же транзакции (`jobs.enqueue(…, { tx })`), и воркер видит ее только после коммита. Получается транзакционный "ящик исходящих" без правки каждой транзакции. Обработчик собирает представления той же функцией, что и список, и через `UserEvents` (шина в памяти, как `RunEvents`) отдает `notification.new` адресатам и `notification.read` автору. Повтор задачи после рестарта дает дубль толчка, клиент сливает их по `id`.
- Источник правды: строка в БД, сокет дает только толчок. Восстановление пакетов socket.io живет в памяти процесса и теряется при рестарте, поэтому клиент сверяется по REST при подключении и переподключении сокета, при открытии колокольчика и при возврате во вкладку.
- Звук и системные уведомления настраиваются на устройстве. Звук играет только для "ждет вас" и только когда ни одна вкладка RemarkRound не в фокусе. Системное уведомление браузера включается переключателем, разрешение запрашивается только по клику, в тексте номер и раунд без сути. Сервер о них не знает.

## Последствия

- Колокольчик работает, пока открыта вкладка: писем и push-сервиса нет (ADR 013 в силе). Кто не открывает продукт, по-прежнему не узнает о своей очереди.
- Инстанс API один: `UserEvents` и комнаты socket.io живут в памяти процесса. На втором инстансе толчок дойдет только до сокетов того процесса, где выполнилась задача `notify_push`, а список по REST останется верным. Второму инстансу нужен тот же Redis-адаптер socket.io, что и комнатам замечаний (docs/ARCHITECTURE.md, "Один инстанс API").
- Задача ставится на каждое событие с адресатами. Импорт журнала уведомлений не дает (`import` никому не приходит), а разбор 200 строк дает 200 предложений руководителю и столько же задач `notify_push`. Разом их идет не больше двух из восьми слотов воркера, прогонам графа и индексации места хватает.
- Миграция `20260924100000_notifications` только добавляет таблицу, индексы и четыре внешних ключа `ON DELETE CASCADE`. Каскад от строки истории проходит триггер `rr_append_only`.
- Спеки: `notifications/audience.spec` (таблица правил, регресс `retest`/`cancel`), `notifications/notifications.spec` (рассылка, автор и отключенные, "действовать = прочитать", ADR 007, смена роли и удаление, страницы, прочтение, MCP 404, изоляция SAVEPOINT), `gateway/ws.notifications.spec` (толчок, вторая вкладка, MCP-сокет, `notification.sync`), `remarks/labels.contract.spec` (у каждого правила есть фраза на экране).
