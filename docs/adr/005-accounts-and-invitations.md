# ADR 005: Аккаунты, стороны и приглашения (проект = команда)

Дата: 2026-09-06  
Статус: принято. Уточнено ADR 006 (2026-09-07): регистрация в production только по ссылке приглашения, приглашение принимается только по ссылке (auto-accept по e-mail отменен), право создавать проекты стало флагом, который выдает администратор инстанса, токен ссылки хранится хэшем и живет 7 дней. Изменено ADR 013 (2026-09-17): почты нет, зарегистрированного PM тоже приглашает, человек принимает приглашение в колокольчике.

## Контекст

До этого решения пользователи появлялись только из seed, единственным маршрутом auth был вход, участников добавлял `admin`, и только уже существующих. Для работы в компании нужны самостоятельная регистрация, сборка команды руководителем приемки и приглашение заказчика. Правило "один пользователь, несколько проектов, в каждом своя роль" и SQL-тенанси при этом не меняются. Почты в компании для пилота нет, а горизонтальное масштабирование не нужно: сервер один.

## Решение

- Регистрация открыта. `POST /auth/register` принимает имя, e-mail, пароль и сторону `preferredRole ∈ {business, pm, developer}`. Без проекта человек видит экран ожидания (`/projects`), который опрашивает `GET /auth/me`.
- Сторона служит подсказкой. Роль в проекте всегда задает `Membership.role`, ее ставит руководитель приемки. Единственное право стороны: `preferredRole = pm` создает проекты (`POST /projects`) и становится в них `pm`. Роль `admin` создатель не получает, потому что admin не разбирает и не решает. Сторону можно поменять в профиле.
- Отдельной сущности "Команда/Организация" нет, команду задает проект: участников в каждый проект PM добавляет отдельно. Вопрос пересматривается, если PM устанут звать одних и тех же разработчиков.
- Участников ведут `pm` и `admin`: `GET/POST /projects/:id/members`, `PATCH/DELETE …/members/:userId`. В проекте всегда остается хотя бы один pm (409). Удаление снимает membership и приглашение на этот e-mail и выкидывает сокеты человека из комнат проекта (`TenancyService.revoke` → `RemarkGateway`).
- Приглашение работает без почты. Незнакомый e-mail → `Invitation { projectId, email, role, token, expiresAt = 30 дней }`, ссылку `/join/<token>` PM копирует и отправляет сам. Приглашение принимается регистрацией или входом с этим e-mail (auto-accept в `login`, `register`, `me`) либо по token уже вошедшим пользователем. E-mail при этом может отличаться: ссылка отправлена адресно. На принятое приглашение ответ 410, на отозванное или истекшее 404.
- Смена пароля означает выход везде. `User.passwordChangedAt`, каждый JWT несет `ts` (мс выпуска), токен с более ранним `ts` получает 401, включая 30-дневные MCP-токены (Cursor перевыпускает). Неверный текущий пароль дает 422: на 401 фронт разлогинивает. `passwordHash` nullable: это задел под вход через Google.
- MCP-токен живет только в своем проекте: `JwtAuthGuard` отдает 404 на любой маршрут, где `projectId` в URL не равен скоупу (`/projects`, `/auth/*`, `/invitations/*`).
- Демо-персоны есть только на демо-стенде: `GET /auth/options { demoLogins }` из `DEMO_LOGINS` (по умолчанию в production выключено). Seed в production отказывается работать.

## Последствия

- Тесты `accounts.spec`, `members.spec` и расширенный `tenancy.leakage.spec` фиксируют: регистрация дает пустой membership; проект создает только сторона pm; заказчик и разработчик не видят участников; последний pm не снимается; удаленный сразу теряет доступ (REST 404, WS join 404); старые токены после смены пароля получают 401.
- Регистрация раскрывает, занят ли e-mail (409). Для одной компании это приемлемо. Вход и регистрация ограничены `THROTTLE_AUTH_LIMIT` с IP.
- Токен приглашения работает как bearer: у кого ссылка, тот и входит с этой ролью. Смягчение: срок 30 дней и отзыв.
- Хук отзыва WS и лимиты работают в одном процессе. Для второго инстанса API нужна внешняя шина (Redis).
- Не сделаны "забыли пароль", письма и подтверждение e-mail.
