# ADR 005 — Аккаунты, стороны и приглашения: проект = команда

Дата: 2026-09-06  
Статус: принято

## Контекст

До фазы 11 пользователи появлялись только из seed, единственный маршрут auth — вход, участников добавлял `admin` и только уже существующих. Для работы в компании нужны самостоятельная регистрация, сборка команды руководителем приёмки и приглашение заказчика — при этом доктрина §3.2 («один пользователь — несколько проектов, в каждом своя роль») и SQL-тенанси не меняются. Почты в компании для пилота нет, а горизонтальное масштабирование не нужно: один сервер.

## Решение

- **Регистрация открыта**: `POST /auth/register` — имя, e-mail, пароль, сторона `preferredRole ∈ {business, pm, developer}`. Без проекта человек видит экран ожидания (`/projects`), который опрашивает `GET /auth/me`.
- **Сторона — подсказка, не право.** Роль в проекте — всегда `Membership.role`, её ставит руководитель приёмки. Единственное право стороны: `preferredRole = pm` создаёт проекты (`POST /projects`) и становится `pm` проекта, а не `admin` (admin не разбирает и не решает). Сторону можно поменять в профиле.
- **Проект = команда.** Отдельной сущности «Команда/Организация» нет: участников в каждый проект PM добавляет отдельно. Вернуться к вопросу, если PM устанут звать одних и тех же разработчиков.
- **Участников ведут `pm` и `admin`**: `GET/POST /projects/:id/members`, `PATCH/DELETE …/members/:userId`. В проекте всегда остаётся хотя бы один pm (409). Удаление снимает membership, приглашение на этот e-mail и выкидывает сокеты человека из комнат проекта (`TenancyService.revoke` → `RemarkGateway`).
- **Приглашение без почты.** Незнакомый e-mail → `Invitation { projectId, email, role, token, expiresAt = 30 дней }`; ссылку `/join/<token>` PM копирует и отправляет сам. Принимается регистрацией или входом с этим e-mail (auto-accept в `login`, `register`, `me`) либо по token уже вошедшим пользователем — e-mail может отличаться, ссылка отправлена адресно. Принятое — 410, отозванное или истёкшее — 404.
- **Смена пароля = выход везде.** `User.passwordChangedAt`; каждый JWT несёт `ts` (мс выпуска), токен с `ts` раньше — 401, включая 30-дневные MCP-токены (Cursor перевыпускает). Неверный текущий пароль — 422, не 401 (фронт на 401 разлогинивает). `passwordHash` nullable — задел под вход через Google.
- **MCP-токен живёт только в своём проекте**: `JwtAuthGuard` отдаёт 404 на любой маршрут, где `projectId` в URL не равен скоупу (`/projects`, `/auth/*`, `/invitations/*`).
- **Демо-персоны только на демо-стенде**: `GET /auth/options { demoLogins }` из `DEMO_LOGINS` (по умолчанию выключено в production); seed в production отказывается работать.

## Последствия

- Тесты `accounts.spec`, `members.spec`, расширенный `tenancy.leakage.spec` фиксируют: регистрация → пустой membership; только сторона pm создаёт проект; заказчик и разработчик не видят участников; последний pm не снимается; удалённый теряет доступ сразу (REST 404, WS join 404); старые токены после смены пароля — 401.
- Регистрация раскрывает, занят ли e-mail (409), — для одной компании приемлемо; вход и регистрация ограничены `THROTTLE_AUTH_LIMIT` с IP.
- Токен приглашения — bearer-способность: у кого ссылка, тот и входит с этой ролью. Смягчение — 30 дней и отзыв.
- Хук отзыва WS и лимиты — в одном процессе: для второго инстанса API нужна внешняя шина (Redis), это отдельный этап.
- «Забыли пароль», письма и подтверждение e-mail — вместе с входом через Google.
