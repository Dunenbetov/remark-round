# ADR 006 — Контур доступа для компании: приглашение только по ссылке, регистрация по приглашению, администратор инстанса

Дата: 2026-09-07  
Статус: принято. Уточняет ADR 005 (пункты «регистрация открыта», «сторона pm создаёт проекты», auto-accept по e-mail — отменены). Дополнено 17.09.2026 (ревью беты A-1): администратор приглашает руководителя приёмки без проекта — см. «Дополнение» в конце.

## Контекст

Аудит готовности (6 сентября 2026) показал четыре дыры контура доступа, каждая из которых для крупной компании — блокер:

1. Приглашение принималось по совпадению e-mail при регистрации, входе и `GET /auth/me`. Почта не подтверждается, значит место в чужом проекте (с ТЗ и кадрами заказчика) забирал тот, кто первым регистрировал угаданный адрес.
2. Регистрация была открыта всем из интернета, а самоназначаемая «сторона pm» давала право создавать проекты — то есть тратить бюджет модели и диск.
3. Сырой токен ссылки хранился в БД и отдавался каждому pm/admin проекта в `GET /members`; жил 30 дней.
4. Не было администратора инстанса: некому отключить уволенного во всех проектах сразу, отозвать его токены (MCP — на 30 дней) и ответить «кто имеет доступ».

## Решение

- **Приглашение принимается только по ссылке.** `acceptPendingByEmail` удалён. Пути: регистрация с `inviteToken` (ссылка проверяется до создания пользователя) и `POST /invitations/:token/accept` вошедшим. Совпадение e-mail без ссылки не даёт ничего; если человек зарегистрировался сам, PM добавляет его напрямую по e-mail — ожидающая ссылка при этом снимается.
- **Токен — один раз, в БД — хэш.** `Invitation.tokenHash = sha256(token)`; сырой токен приходит в ответе на создание и по `POST /projects/:id/invitations/:invId/link` («Новая ссылка»: прежняя перестаёт работать, срок продлевается). В списке участников токена нет; `GET /invitations/:token` не показывает e-mail приглашённого. Срок — 7 дней.
- **Режим регистрации.** `REGISTRATION_MODE = open | invite_only`; без значения в production — `invite_only`, иначе `open`. В `invite_only` регистрация без живой ссылки — 403, кроме: e-mail с домена из `REGISTRATION_DOMAINS` (сотрудники компании) и e-mail из `ADMIN_EMAILS` (первый человек в пустой системе). `GET /auth/options` отдаёт `registration`, вход прячет «Зарегистрироваться».
- **Право создавать проекты — явный флаг** `User.canCreateProjects`, выдаёт администратор инстанса; у него самого есть всегда. `preferredRole` остаётся подсказкой для экранов и ничего не разрешает.
- **Администратор инстанса** — e-mail из `ADMIN_EMAILS` (не проектная роль `admin`). `/admin/users`, `/admin/projects`, `PATCH /admin/users/:id { canCreateProjects?, disabled? }`, `POST /admin/users/:id/revoke-sessions`. Отключение (`User.disabledAt`) — вход 403, все токены и сокеты недействительны сразу; включение обратно не оживляет старые токены. `User.tokenVersion` в JWT (`tv`) — «завершить все сессии» без смены пароля.
- **Смена роли отзывает WS-контекст** (`TenancyService.revoke` в `changeRole`), как удаление участника: бывший pm не продолжает решать в открытых комнатах.

## Последствия

- Пилот в компании стартует так: `ADMIN_EMAILS` в `.env` → администратор регистрируется → выдаёт право создавать проекты руководителю приёмки → тот создаёт проект и рассылает ссылки. Демо-стенд (`docker compose up`) остаётся открытым: `REGISTRATION_MODE` не задан, `NODE_ENV=development`, seed даёт pm право создавать проекты, `ADMIN_EMAILS=pm@remarkround.dev`.
- Существующие ссылки после миграции `20260907100000_access_contour` продолжают работать: хэш посчитан на месте. Существующие pm не получают право создавать проекты автоматически — его выдаёт администратор (или seed на демо).
- UX-компромисс: письма по-прежнему нет, поэтому пропавшую ссылку нельзя «показать ещё раз» — только выпустить новую. Это цена хранения хэша; кнопка «Новая ссылка» стоит рядом с каждым приглашением.
- Не сделано здесь (см. аудит): подтверждение e-mail и сброс пароля (нужен SMTP), SSO, сверка e-mail при принятии по ссылке, поштучный отзыв MCP-токенов, журнал событий безопасности. Отключение и отзыв сессий — через `tokenVersion`, что позже станет основой и для «выйти везде» самому себе.
- Тесты: `accounts.spec` (режимы регистрации, флаг права), `members.spec` (токен один раз, «Новая ссылка», e-mail без ссылки ничего не даёт, смена роли рвёт комнату), `admin.spec` (403/404 для не-админов, отключение и отзыв — REST, MCP, WS).

## Дополнение 17.09.2026 — приглашение руководителя без проекта (A-1)

Разрыв: в `invite_only` человек не с домена компании не мог появиться в системе, пока какой-нибудь PM не создаст проект и не позовёт его, а «первого PM» администратор мог сделать только из уже зарегистрированного. Решение: `Invitation.projectId` стал nullable; `POST /admin/invitations { email }` (только администратор инстанса) создаёт приглашение без проекта с ролью `pm` и шлёт письмо «приглашение руководителя приёмки»; для уже зарегистрированного e-mail право `canCreateProjects` выдаётся сразу (`{ kind: 'user' }`). `GET /invitations/:token` отдаёт `kind: 'instance'`, `projectName: null`; принятие (регистрацией или вошедшим) ставит `canCreateProjects = true` и membership не создаёт — проект человек создаёт сам. Одна строка на e-mail держится сервисом (уникальность `(projectId, email)` NULL не покрывает); отдельного флага нет — признак инстанс-приглашения `projectId IS NULL`. Bootstrap теперь: `ADMIN_EMAILS` → администратор регистрируется → приглашает руководителя письмом → тот создаёт проект и зовёт участников. Ответ регистрации по такой ссылке строится по свежей строке пользователя (иначе `canCreateProjects: false` до перелогина). Спеки: `admin.spec` («приглашает руководителя без проекта»).

## Дополнение 17.09.2026 — проектная роль `admin` снаружи не выдаётся (A-2)

`POST/PATCH /projects/:id/members` принимают только `business | pm | developer`: проектный `admin` (≈ pm без права решать) путался с администратором инстанса, а интерфейс его и не предлагал. Значение остаётся в enum `Role` (seed и харнесс тестов пишут его через Prisma; `@Roles('pm', 'admin')` на маршрутах продолжают работать) — удаление из enum миграцией после беты.
