# ADR 006: Контур доступа для компании (приглашение только по ссылке, регистрация по приглашению, администратор инстанса)

Дата: 2026-09-07  
Статус: принято. Уточняет ADR 005: пункты "регистрация открыта", "сторона pm создает проекты" и auto-accept по e-mail отменены. Дополнено 17.09.2026: администратор приглашает руководителя приемки без проекта (см. дополнения в конце).

## Контекст

Аудит готовности 6 сентября 2026 нашел в контуре доступа четыре дыры. Для крупной компании каждая из них блокирует запуск:

1. Приглашение принималось по совпадению e-mail при регистрации, входе и `GET /auth/me`. Почта не подтверждается, значит место в чужом проекте (с ТЗ и кадрами заказчика) забирал тот, кто первым регистрировал угаданный адрес.
2. Регистрация была открыта всем из интернета, а самоназначаемая "сторона pm" давала право создавать проекты, то есть тратить бюджет модели и диск.
3. Сырой токен ссылки хранился в БД и отдавался каждому pm/admin проекта в `GET /members`. Жил он 30 дней.
4. Не было администратора инстанса: некому отключить уволенного во всех проектах сразу, отозвать его токены (MCP-токен живет 30 дней) и ответить, у кого есть доступ.

## Решение

- Приглашение принимается только по ссылке. `acceptPendingByEmail` удален. Путей два: регистрация с `inviteToken` (ссылка проверяется до создания пользователя) и `POST /invitations/:token/accept` вошедшим. Совпадение e-mail без ссылки не дает ничего. Если человек зарегистрировался сам, PM добавляет его напрямую по e-mail, ожидающая ссылка при этом снимается. 17.09.2026 (ADR 013): напрямую больше никого не добавляем, зарегистрированному тоже создается приглашение. Он принимает его ссылкой или в колокольчике (`/auth/invitations`) по совпадению e-mail, PM видит `inviteeName`.
- Токен выдается один раз, в БД лежит хэш: `Invitation.tokenHash = sha256(token)`. Сырой токен приходит в ответе на создание и по `POST /projects/:id/invitations/:invId/link` ("Новая ссылка": прежняя перестает работать, срок продлевается). В списке участников токена нет, `GET /invitations/:token` не показывает e-mail приглашенного. Срок 7 дней.
- Режим регистрации задает `REGISTRATION_MODE = open | invite_only`. Без значения в production действует `invite_only`, иначе `open`. В `invite_only` регистрация без живой ссылки получает 403. Исключения: e-mail с домена из `REGISTRATION_DOMAINS` (сотрудники компании) и e-mail из `ADMIN_EMAILS` (первый человек в пустой системе). `GET /auth/options` отдает `registration`, и экран входа прячет "Зарегистрироваться".
- Право создавать проекты задает явный флаг `User.canCreateProjects`. Его выдает администратор инстанса, у самого администратора это право есть всегда. `preferredRole` остается подсказкой для экранов и ничего не разрешает.
- Администратора инстанса определяет e-mail из `ADMIN_EMAILS`, с проектной ролью `admin` он не связан. Маршруты: `/admin/users`, `/admin/projects`, `PATCH /admin/users/:id { canCreateProjects?, disabled? }`, `POST /admin/users/:id/revoke-sessions`. После отключения (`User.disabledAt`) вход дает 403, все токены и сокеты сразу недействительны. Включение обратно старые токены не оживляет. `User.tokenVersion` в JWT (`tv`) позволяет "завершить все сессии" без смены пароля.
- Смена роли отзывает WS-контекст (`TenancyService.revoke` в `changeRole`), как и удаление участника: бывший pm не продолжает решать в открытых комнатах.

## Последствия

- Пилот в компании стартует так: `ADMIN_EMAILS` в `.env` → администратор регистрируется → выдает право создавать проекты руководителю приемки → тот создает проект и рассылает ссылки. Демо-стенд (`docker compose up`) остается открытым: `REGISTRATION_MODE` не задан, `NODE_ENV=development`, seed дает pm право создавать проекты, `ADMIN_EMAILS=admin@remarkround.dev` (с 20.09 это отдельная демо-персона, см. дополнение ниже).
- Существующие ссылки после миграции `20260907100000_access_contour` продолжают работать: хэш посчитан на месте. Существующие pm не получают право создавать проекты автоматически, его выдает администратор (на демо seed).
- Писем по-прежнему нет, поэтому пропавшую ссылку нельзя "показать еще раз", можно только выпустить новую. Это цена хранения хэша. Кнопка "Новая ссылка" стоит рядом с каждым приглашением.
- Не сделано в этом ADR: подтверждение e-mail и сброс пароля (нужен SMTP), SSO, сверка e-mail при принятии по ссылке, поштучный отзыв MCP-токенов, журнал событий безопасности. Отключение и отзыв сессий работают через `tokenVersion`.
- Тесты: `accounts.spec` (режимы регистрации, флаг права), `members.spec` (токен один раз, "Новая ссылка", e-mail без ссылки ничего не дает, смена роли рвет комнату), `admin.spec` (403/404 для не-админов, отключение и отзыв через REST, MCP, WS).

## Дополнение 17.09.2026: приглашение руководителя без проекта

В `invite_only` человек не с домена компании не мог появиться в системе, пока какой-нибудь PM не создаст проект и не позовет его, а "первого PM" администратор мог сделать только из уже зарегистрированного.

`Invitation.projectId` стал nullable. `POST /admin/invitations { email }` (только администратор инстанса) создает приглашение без проекта с ролью `pm` и шлет письмо "приглашение руководителя приемки" (по ADR 013 письма нет, ссылку администратор отправляет сам). Для уже зарегистрированного e-mail право `canCreateProjects` выдается сразу (`{ kind: 'user' }`). `GET /invitations/:token` отдает `kind: 'instance'` и `projectName: null`. Принятие (регистрацией или вошедшим) ставит `canCreateProjects = true` и membership не создает: проект человек создает сам. Одну строку на e-mail держит сервис, потому что уникальность `(projectId, email)` NULL не покрывает. Отдельного флага нет, признак инстанс-приглашения: `projectId IS NULL`. Bootstrap теперь такой: `ADMIN_EMAILS` → администратор регистрируется → приглашает руководителя ссылкой → тот создает проект и зовет участников. Ответ регистрации по такой ссылке строится по свежей строке пользователя, иначе до перелогина было бы `canCreateProjects: false`. Спеки: `admin.spec` ("приглашает руководителя без проекта").

## Дополнение 17.09.2026: администратор без стороны, открытая регистрация на бете

Решения 17.09.2026:

- Администратор инстанса получает отдельную скрытую роль "Администратор" вместо стороны. E-mail из `ADMIN_EMAILS` (на 17.09 это ровно один человек) не выбирает `business | pm | developer`. При регистрации DTO по-прежнему требует сторону от всех, но для администратора сервер ее игнорирует и хранит `preferredRole = null`. `toAuthUser` (ответы `login`/`register`/`me`, `PATCH /auth/profile`) отдает `preferredRole: null`, что бы ни лежало в строке. В SPA у администратора нет переключателя стороны в профиле, в шапке и профиле стоит подпись "Администратор" (`ROLE_ADMIN`), а корень без проектов ведет в `/admin` вместо "Вас еще не добавили в проект". Проектные роли остаются за руководителем приемки проекта, `/admin/*` охраняется как прежде. Спека: `accounts.spec` (тест "скрытая роль без стороны").
- Регистрация на бете открыта: `REGISTRATION_MODE=open` задан переменной Railway (`docs/PROD-RAILWAY.md`). Код не менялся: без значения в production по-прежнему действует `invite_only`.
- Право создавать проекты по-прежнему выдает администратор (`canCreateProjects`, `PATCH /admin/users/:id` или приглашение руководителя без проекта). Открытая регистрация дает аккаунт без проекта.

## Дополнение 17.09.2026: проектная роль `admin` снаружи не выдается

`POST/PATCH /projects/:id/members` принимают только `business | pm | developer`. Проектный `admin` (≈ pm без права решать) путался с администратором инстанса, а интерфейс его и не предлагал. Значение остается в enum `Role`: seed и харнесс тестов пишут его через Prisma, `@Roles('pm', 'admin')` на маршрутах продолжают работать.

## Дополнение 20.09.2026: администратору только администрирование

Решение 20.09.2026: администратор инстанса видит только `/admin` и свой профиль, где может сменить пароль. Проекты, журнал, "Вас еще не добавили в проект", колокольчик приглашений и старые ссылки ему не показываются: корень и любой адрес проекта ведут в `/admin` (`homeUrl`, `projectGuard`, `legacyUrlGuard`, `notInstanceAdminGuard` на `/projects`). Сервер держит то же правило: `POST /projects/:id/members` с e-mail из `ADMIN_EMAILS` отвечает 409 (администратор инстанса не участвует в проектах), принятие проектного приглашения администратором (ссылкой или из колокольчика) тоже дает 409. Для работы в проекте у человека должен быть отдельный аккаунт. На демо-стенде администратор является отдельной демо-персоной `admin@remarkround.dev` (`ADMIN_EMAILS` в `docker-compose.yml`), демо-PM больше не администратор. Спеки: `admin.spec` ("в проекты не входит").
