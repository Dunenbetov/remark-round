# ADR 014 — Оркестратор: LangGraph.js, а не CrewAI / Parlant / свой цикл в Nest; свой чекпоинтер

Дата: 2026-09-19 (записано задним числом: выбор сделан в доктрине 20.08, граф написан 03.09)  
Статус: принято

## Контекст

Что должен уметь оркестратор разбора замечания (`REMARKROUND.md` §4.6, §7.2):

1. **Ветки и циклы с жёстким лимитом.** Переписать запрос — не больше 2 раз, дальше classify работает с тем, что нашлось. Переделать черновик, не прошедший проверку, — не больше 2 раз, на третьем провале код ставит честное `cannot_tell`. Бесконечных вызовов модели нет.
2. **Пауза на решение человека дольше HTTP-запроса** — часы и дни. Она переживает перезапуск API и деплой, а после «Не та цитата из ТЗ» тот же прогон продолжается с сохранённым состоянием.
3. **Состояние в той же Postgres**, где замечания: один бэкап, фильтр проекта в SQL.
4. **Шаги видны в трейсе** Langfuse: какие ноды прошли и сколько раз повторились.
5. **Один язык и один процесс с доменом.** Вся запись идёт через `RemarksService` в Nest, и ноды должны звать его напрямую, а не по сети.
6. **Цена поддержки.** Проект ведёт один человек, фронтендер; код пишут агенты.

Мультиагентность не нужна: одна карточка, один поток, решает один человек. «Мультиагентный цирк (researcher + critic + manager)» доктрина запрещает (`REMARKROUND.md` §15).

## Варианты простыми словами

- **LangGraph.js** (`@langchain/langgraph`) — библиотека для TypeScript. Работа описывается графом: общее состояние (как стор с редьюсерами), ноды возвращают патч к нему, условные рёбра работают как route guards. Чекпоинтер сохраняет состояние после каждого шага, `interrupt()` ставит граф на паузу, `new Command({ resume })` будит его в том же `thread_id`.
- **CrewAI** — фреймворк на Python. Основная идея — «команда» (crew) агентов с ролью, целью и предысторией, которые делят задачи между собой. По документации на 18.09 у него есть и Flows: цепочки шагов с ветками (`@router`), сохранением состояния (`@persist`, по умолчанию в SQLite) и паузой на человека (`@human_feedback`). Так что довод «CrewAI этого не умеет» был бы неверным.
- **Parlant** — движок диалоговых агентов для общения с клиентом, тоже на Python: правила поведения «условие → действие» (guidelines), сценарии разговора (journeys), отдельный сервер. Из TypeScript к нему ходят REST-клиентом.
- **Свой цикл в Nest** — `while` и `if` в сервисе плюс своя таблица состояния.

## Сравнение

Выбор сделан в доктрине 20.08 (`REMARKROUND.md` §4.6, §5, §15): CrewAI, Parlant и Python-ядро исключены сразу, **прототипов не делали**. Сравнение ниже — по их документации, собрано 18.09 задним числом, чтобы проверить, держится ли довод. Свой цикл тоже не прототипировали: оценка — по тому, что пришлось бы написать самим.

| Критерий | LangGraph.js | CrewAI | Parlant | Свой цикл в Nest |
|---|---|---|---|---|
| Язык и рантайм | TypeScript, тот же процесс Nest | Python: второй рантайм и второй деплой, домен звать по HTTP | Python-сервер рядом, из Nest — REST-клиент | TypeScript, тот же процесс |
| Циклы с лимитом | условные рёбра и счётчики в состоянии, плюс `recursionLimit` | Flows: `@router` и счётчики в своём состоянии | сценарии разговора с переходами — про диалог, не про повтор генерации | `while` со счётчиком — просто |
| Пауза с сохранением в БД | `interrupt` и чекпоинтер; наш на Postgres — 123 строки | `@persist` (по умолчанию SQLite) и `@human_feedback`; хранение в нашей Postgres не проверяли | сессии диалога на своём сервере; не проверяли | писать самим: сериализация, продолжение с места в любом процессе, идемпотентность шагов |
| Трассировка нод | `CallbackHandler` из `@langfuse/langchain`: ноды становятся спанами без своего кода | не проверяли | своя «объяснимость» решений; с нашим Langfuse не проверяли | спаны руками на каждый шаг |
| Цена поддержки | одна зависимость и немного LangChain; цена — в разделе «Последствия» | второй язык и второй сервис; модель «команды агентов» нам не нужна | второй сервис; продукт для чата с клиентом, а у нас карточка и кнопка | всё своё и всё под своими тестами |

## Решение

LangGraph.js внутри `AgentModule` API: два графа (`buildTriageGraph`, `buildRetestGraph`), состояние через `Annotation.Root`, чекпоинтер — свой `PrismaCheckpointSaver` на таблице `GraphCheckpoint`, `thread_id = AgentRun.id`. От LangChain берём только граф: модель вызывается официальным SDK `openai`, агентов с tool-calling нет. Как граф устроен и запускается — [GRAPH.md](../GRAPH.md).

Против своего цикла решил пункт 2: сохранение после каждого шага, продолжение с места остановки в любом процессе и спаны по шагам LangGraph даёт готовыми. Против CrewAI и Parlant — пункты 5 и 6: второй язык и второй сервис ради возможностей, которые нам нужны в малой части, при том что домен и единственный путь записи живут в Nest.

## Почему свой чекпоинтер, а не `@langchain/langgraph-checkpoint-postgres`

Факты из кода и истории:

- Таблица `GraphCheckpoint` со ссылкой на `AgentRun` была в модели данных с первой миграции 20.08 (`packages/db/prisma/migrations/20250820120000_init`, `REMARKROUND.md` §8). В фазе 6 (03.09) миграция `20260903200000_graph_checkpoint_fields` добавила колонки, которых требует чекпоинтер: `ns`, `checkpointId`, `parentId`, `metadata`, `writes`.
- Чекпоинты удаляются каскадом вместе с `AgentRun` (`packages/db/prisma/schema.prisma:402`). Отмена и повтор старта чистят thread (`deleteThread`), ретеншн — один запрос Prisma с фильтром по статусу прогона (`apps/api/src/agent/agent.service.ts:134-139`).
- `PostgresSaver`, по документации LangGraph, принимает пул `pg` и создаёт свои таблицы своими миграциями через `setup()` (проверено 18.09). У нас появились бы второй пул соединений рядом с Prisma, второй механизм миграций вне `prisma migrate` и таблицы вне схемы Prisma.
- Реализация — порт `MemorySaver`: тот же сериализатор, только строки в Postgres. `putWrites` — атомарное слияние jsonb, чтобы параллельные записи одного шага не затирали друг друга (`apps/api/src/agent/prisma-checkpointer.ts:86-89`).

Честно: коммит `44fd3b3` (03.09), где появился чекпоинтер, причину не называет — доводы выше собраны по коду и схеме задним числом. Производительность против `PostgresSaver` не сравнивали. Официальный набор проверок чекпоинтеров (`@langchain/langgraph-checkpoint-validation`) на нашем не запускали.

## Последствия и цена

- Граф живёт в процессе API: тяжёлый прогон делит CPU с REST и WebSocket, а работает один инстанс API (`docs/ARCHITECTURE.md`, «Один инстанс API»).
- При resume LangGraph перезапускает ноду с `interrupt()` с начала. Поэтому запись предложения вынесена в отдельную ноду `propose` — так советует и документация LangGraph.
- Состояние обязано сериализоваться в JSON, и каждый шаг пишет полный снимок — отсюда ретеншн чекпоинтов 7 дней.
- 123 строки своего чекпоинтера сопровождаем сами: при обновлении `@langchain/langgraph-checkpoint` может измениться контракт `BaseCheckpointSaver`.
- Тестом не доказано, что спящий граф разбудит другой экземпляр API: это держится на устройстве (чекпоинт в Postgres), отдельной спеки нет.
- Цикл «Не та цитата из ТЗ» по числу не ограничен, суточный бюджет на продолжении не проверяется. Нода `bind_to_clause` в боевом режиме решает только, нужен ли rewrite, а ребро `faithfulness_gate → bind_to_clause` фактически повторяет classify и draft — наследие ранней схемы. Всё это осознанно и описано в [GRAPH.md](../GRAPH.md); после M1 граф меняем только через замер — любая правка сдвигает цифры EVALS.md.

## Когда пересмотреть

- Появятся несколько агентов с разными ролями и tool-calling — сравнить заново CrewAI Flows и мультиагентные схемы LangGraph.
- Граф понадобится вынести из процесса API (нагрузка, второй инстанс) — сначала общая шина событий и отмена через базу (`docs/ARCHITECTURE.md`), затем отдельный процесс-воркер на том же коде.
- Обновление LangGraph сломает контракт чекпоинтера или наш не пройдёт официальные проверки — перейти на `PostgresSaver` с его таблицами.
