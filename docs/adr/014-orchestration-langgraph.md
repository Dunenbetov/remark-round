# ADR 014: Выбор оркестратора (LangGraph.js, CrewAI, Parlant, свой цикл в Nest) и свой чекпоинтер

Дата: 2026-09-19 (записано задним числом: выбор сделан 20.08 при старте проекта, граф написан 03.09)  
Статус: принято

## Контекст

Что должен уметь оркестратор разбора замечания:

1. Ветки и циклы с жестким лимитом. Запрос переписывается не больше 2 раз, дальше classify работает с тем, что нашлось. Черновик, не прошедший проверку, переделывается не больше 2 раз, на третьем провале код ставит `cannot_tell`. Бесконечных вызовов модели нет.
2. Пауза на решение человека дольше HTTP-запроса, на часы и дни. Она должна пережить перезапуск API и деплой: состояние лежит в Postgres, отдельным тестом это не проверено. После "Не та цитата из ТЗ" тот же прогон продолжается с сохраненным состоянием.
3. Состояние в той же Postgres, где замечания: один бэкап, фильтр проекта в SQL.
4. Шаги видны в трейсе Langfuse: какие ноды прошли и сколько раз повторились.
5. Один язык и один процесс с доменом. Вся запись идет через `RemarksService` в Nest, и ноды должны звать его напрямую, без сети.
6. Цена поддержки. Проект ведет один человек, фронтендер.

Мультиагентность не нужна: одна карточка проходит один поток, решает один человек. Схему из нескольких агентов (researcher + critic + manager) исключили при старте проекта.

## Альтернативы

- LangGraph.js (`@langchain/langgraph`): библиотека для TypeScript. Работа описывается графом: общее состояние (как стор с редьюсерами), ноды возвращают патч к нему, условные ребра работают как route guards. Чекпоинтер сохраняет состояние после каждого шага, `interrupt()` ставит граф на паузу, `new Command({ resume })` будит его в том же `thread_id`.
- CrewAI: фреймворк на Python. Основная идея в "команде" (crew) агентов с ролью, целью и предысторией, которые делят задачи между собой. По документации на 18.09 у него есть и Flows: цепочки шагов с ветками (`@router`), сохранением состояния (`@persist`, по умолчанию в SQLite) и паузой на человека (`@human_feedback`). Поэтому довод "CrewAI этого не умеет" был бы неверным.
- Parlant: движок диалоговых агентов для общения с клиентом, тоже на Python. В нем правила поведения "условие → действие" (guidelines), сценарии разговора (journeys) и отдельный сервер. Из TypeScript к нему ходят REST-клиентом.
- Свой цикл в Nest: `while` и `if` в сервисе плюс своя таблица состояния.

### Сравнение

Выбор сделан 20.08 при старте проекта: CrewAI, Parlant и Python-ядро исключили сразу, прототипов не делали. Сравнение ниже собрано 18.09 задним числом по их документации, чтобы проверить, держится ли довод. Свой цикл тоже не прототипировали, его оценка основана на том, что пришлось бы написать самим.

| Критерий | LangGraph.js | CrewAI | Parlant | Свой цикл в Nest |
|---|---|---|---|---|
| Язык и рантайм | TypeScript, тот же процесс Nest | Python: второй рантайм и второй деплой, домен звать по HTTP | Python-сервер рядом, из Nest через REST-клиент | TypeScript, тот же процесс |
| Циклы с лимитом | условные ребра и счетчики в состоянии, плюс `recursionLimit` | Flows: `@router` и счетчики в своем состоянии | сценарии разговора с переходами, они для диалога, не для повтора генерации | `while` со счетчиком, просто |
| Пауза с сохранением в БД | `interrupt` и чекпоинтер; наш на Postgres занимает около 150 строк | `@persist` (по умолчанию SQLite) и `@human_feedback`; хранение в нашей Postgres не проверяли | сессии диалога на своем сервере; не проверяли | писать самим: сериализация, продолжение с места в любом процессе, идемпотентность шагов |
| Трассировка нод | `CallbackHandler` из `@langfuse/langchain`: ноды становятся спанами без своего кода | не проверяли | своя "объяснимость" решений; с нашим Langfuse не проверяли | спаны руками на каждый шаг |
| Цена поддержки | одна зависимость и немного LangChain; цена описана в разделе "Последствия" | второй язык и второй сервис; модель "команды агентов" нам не нужна | второй сервис; продукт для чата с клиентом, у нас карточка и кнопка | все свое и все под своими тестами |

## Решение

LangGraph.js внутри `AgentModule` API. Графов два: `buildTriageGraph` (12 нод, 4 условных перехода) и `buildRetestGraph` (7 нод, 2 условных перехода). Состояние описано через `Annotation.Root`, чекпоинтер свой: `PrismaCheckpointSaver` на таблице `GraphCheckpoint`, `thread_id = AgentRun.id`. От LangChain берем только граф: модель вызывается официальным SDK `openai`, агентов с tool-calling нет. Как граф устроен и запускается: [GRAPH.md](../GRAPH.md).

Против своего цикла решил пункт 2: сохранение после каждого шага, продолжение с места остановки в любом процессе и спаны по шагам LangGraph дает готовыми. Против CrewAI и Parlant решили пункты 5 и 6: второй язык и второй сервис ради возможностей, которые нам нужны в малой части, при том что домен и единственный путь записи живут в Nest.

## Чекпоинтер: свой или `@langchain/langgraph-checkpoint-postgres`

Факты из кода и истории:

- Таблица `GraphCheckpoint` со ссылкой на `AgentRun` была в модели данных с первой миграции 20.08 (`packages/db/prisma/migrations/20250820120000_init`). 03.09 миграция `20260903200000_graph_checkpoint_fields` добавила колонки, которых требует чекпоинтер: `ns`, `checkpointId`, `parentId`, `metadata`, `writes`.
- Чекпоинты удаляются каскадом вместе с `AgentRun` (модель `GraphCheckpoint` в `packages/db/prisma/schema.prisma`, `onDelete: Cascade`). Отмена и повтор старта чистят thread (`deleteThread`). Ретеншн делается одним запросом Prisma с фильтром по статусу прогона (`AgentService.pruneCheckpoints` в `apps/api/src/agent/agent.service.ts`).
- `PostgresSaver`, по документации LangGraph, принимает пул `pg` и создает свои таблицы своими миграциями через `setup()` (проверено 18.09). У нас появились бы второй пул соединений рядом с Prisma, второй механизм миграций вне `prisma migrate` и таблицы вне схемы Prisma.
- Реализация является портом `MemorySaver`: тот же сериализатор, только строки в Postgres. `putWrites` делает атомарное слияние jsonb, чтобы параллельные записи одного шага не затирали друг друга (`PrismaCheckpointSaver.putWrites` в `apps/api/src/agent/prisma-checkpointer.ts`).

Коммит `44fd3b3` (03.09), где появился чекпоинтер, причину не называет: доводы выше собраны по коду и схеме задним числом. Производительность против `PostgresSaver` не сравнивали. Официальный набор проверок чекпоинтеров (`@langchain/langgraph-checkpoint-validation`) на нашем не запускали.

## Последствия

- Граф живет в процессе API: тяжелый прогон делит CPU с REST и WebSocket, а инстанс API один (`docs/ARCHITECTURE.md`, "Один инстанс API").
- При resume LangGraph перезапускает ноду с `interrupt()` с начала. Поэтому запись предложения вынесена в отдельную ноду `propose`, так советует и документация LangGraph.
- Состояние обязано сериализоваться в JSON, и каждый шаг пишет полный снимок, поэтому ретеншн чекпоинтов 7 дней.
- Около 150 строк своего чекпоинтера сопровождаем сами: при обновлении `@langchain/langgraph-checkpoint` может измениться контракт `BaseCheckpointSaver`.
- Тестом не доказано, что спящий граф разбудит другой экземпляр API. Это держится на устройстве (чекпоинт в Postgres), отдельной спеки нет.
- Цикл "Не та цитата из ТЗ" по числу не ограничен, суточный бюджет на продолжении не проверяется. Нода `bind_to_clause` в боевом режиме решает только, нужен ли rewrite, а ребро `faithfulness_gate → bind_to_clause` фактически повторяет classify и draft, это наследие ранней схемы. Все это оставлено осознанно и описано в [GRAPH.md](../GRAPH.md). После замеров 20-21.09 граф меняется только через замер: любая правка сдвигает цифры EVALS.md.

## Когда пересмотреть

- В разборе появятся несколько агентов с разными ролями и tool-calling. Тогда сравнение с CrewAI Flows и мультиагентными схемами LangGraph проводится заново.
- Граф нужно вынести из процесса API (нагрузка, второй инстанс). Для этого сначала нужны общая шина событий и отмена через базу (`docs/ARCHITECTURE.md`), затем отдельный процесс-воркер на том же коде.
- Обновление LangGraph ломает контракт чекпоинтера, или наш чекпоинтер не проходит официальные проверки. Тогда переходим на `PostgresSaver` с его таблицами.
